# QiCardMesh 通信协议

本文档由 `protobuf/qicardmesh.proto` 定义，并结合 `QiCardMeshAgent` 的实际实现整理。协议描述本地智能卡守护进程如何通过 MQTT 向对端暴露 PC/SC 卡片能力。

权威消息结构以仓库根目录下的 [`protobuf/qicardmesh.proto`](../protobuf/qicardmesh.proto) 为准；Agent 在构建时通过 `prost-build` 生成 Rust 绑定。

---

## 1. 传输与连接

| 项 | 约定 |
| --- | --- |
| 协议 | MQTT over TLS（`mqtts`） |
| 固定端点 | `mqtts://mqtt.cyqi.top:8883` |
| 认证 | MQTT 用户名 / 密码（配置文件提供，不进入主题名或日志） |
| Keep-Alive | 30 秒 |
| QoS | 业务消息统一使用 **AtLeastOnce（QoS 1）** |
| Retain | 不使用（`retain = false`） |
| Payload | Protocol Buffers 二进制（`proto3`，package `qicardmesh`） |

端点属于协议契约的一部分。`QiCardMeshAgent` 启动时会强制使用上述地址；配置文件里的 `mqtt.url` 即使被改写也会被覆盖。

仅验证 TLS 与 CONNECT 认证、不订阅不发布时，可使用：

```powershell
cargo run -p qicardmesh-agent -- --config QiCardMeshAgent/config.yaml --check-mqtt
```

同一 `client_id` 在 Broker 上只允许一条连接；检查前需先停止同身份的 Agent。

## 2. 设备身份与 Client ID

### 2.1 有效用户 ID

配置中的 `user_id` 只是账号前缀。运行时 Agent 会附加本机磁盘指纹，得到**有效身份**：

```text
<effective_user_id> = <配置的 user_id>:<disk_fingerprint>
```

- `user_id` 为空时默认前缀为 `user_id`
- `disk_fingerprint`：对本机主存储标识做 SHA-256，取前 16 字节的十六进制（共 32 个 hex 字符）
  - Windows：优先取第一块物理磁盘的 CIM `SerialNumber`
  - Unix：优先读 `/etc/machine-id` 或 `/var/lib/dbus/machine-id`
  - 均不可用时回退到主机名 + OS 名

示例：`alice:a1b2c3d4e5f6789012345678abcdef01`

### 2.2 MQTT Client ID

```text
client_id = <effective_user_id>
```

Client ID 与有效身份完全一致，用于 Broker 会话去重与主题隔离。

## 3. 主题设计

所有设备相关主题以有效身份为作用域：

| 用途 | 主题 | 方向 | 消息类型 |
| --- | --- | --- | --- |
| 方法调用 | `QiCardMesh/device/<effective_user_id>/method` | 对端 ⇄ Agent | `MethodRequest` / `MethodResponse` |
| 状态通知 | `QiCardMesh/device/<effective_user_id>/notify` | Agent → 对端 | `Notify` |

### 3.1 method 主题

- **请求与响应使用同一主题**
- Agent **订阅**该主题，解码 `MethodRequest`，处理后在**同一主题**发布 `MethodResponse`
- 调用方用 `request_id` 把响应与进行中的请求配对；允许多请求并发在途
- 无法解码的 protobuf 请求会被丢弃（不回复）

### 3.2 notify 主题

- Agent 在连接成功、卡片插拔、进程退出等时刻**单向发布**
- 调用方按需订阅以感知设备与卡片生命周期

## 4. 消息定义

### 4.1 方法请求 `MethodRequest`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `request_id` | `string` | 调用方生成的关联 ID，响应原样带回 |
| `operation` | `Operation` | 要执行的操作 |
| `card_id` | `string` | 目标卡片 ID；`LIST_CARDS` 可为空 |
| `apdu` | `bytes` | 仅 `EXECUTE_APDU` 使用的原始 APDU 命令 |

### 4.2 操作枚举 `Operation`

| 值 | 名称 | 含义 | 成功时 `payload` |
| --- | --- | --- | --- |
| `0` | `OPERATION_UNSPECIFIED` | 未指定（非法） | 无；返回错误 |
| `1` | `LIST_CARDS` | 列出当前会话中的卡片摘要 | `card_list`（`CardList`） |
| `2` | `GET_CARD` | 按 `card_id` 取完整卡片信息 | `card`（`CardInfo`） |
| `3` | `EXECUTE_APDU` | 对指定卡片透传一条 APDU | `apdu`（`ApduResponse`） |

### 4.3 方法响应 `MethodResponse`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `request_id` | `string` | 与请求一致 |
| `success` | `bool` | 是否成功 |
| `error` | `string` | 失败原因；成功时为空字符串 |
| `payload` | `oneof` | 成功时的业务载荷（见下） |

`payload` 三选一：

| oneof 成员 | 类型 | 对应操作 |
| --- | --- | --- |
| `card_list` | `CardList` | `LIST_CARDS` |
| `card` | `CardInfo` | `GET_CARD` |
| `apdu` | `ApduResponse` | `EXECUTE_APDU` |

失败时：`success = false`，`error` 为可读说明，`payload` 为空。常见错误包括：

- `card not found: <card_id>`
- `unsupported operation`
- 后端/PC/SC 传输错误字符串

### 4.4 卡片摘要 `CardSummary` / 列表 `CardList`

`CardList.cards` 为 `CardSummary` 数组。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `card_id` | `string` | 卡片稳定 ID（见第 6 节） |
| `reader_name` | `string` | 读卡器名称 |
| `protocol` | `string` | 后端协议标记（PC/SC 实现中为 `"pcsc"`） |
| `card_name` | `string` | 可读名称（当前实现可为空） |

### 4.5 完整卡片信息 `CardInfo`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `card_id` | `string` | 卡片稳定 ID |
| `reader_name` | `string` | 读卡器名称 |
| `atr` | `bytes` | Answer To Reset |
| `protocol` | `string` | 后端协议标记 |
| `card_name` | `string` | 可读名称 |
| `metadata` | `map<string, string>` | 扩展元数据 |

### 4.6 APDU 响应 `ApduResponse`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `data` | `bytes` | 响应体（**不含**尾部状态字） |
| `sw1` | `uint32` | 状态字高字节 |
| `sw2` | `uint32` | 状态字低字节 |

Agent 从 PC/SC 原始返回中拆分：若长度 ≥ 2，最后两字节分别为 SW1/SW2，前面为 `data`；否则 `data` 为全文且 SW1/SW2 为 `0`。

### 4.7 通知 `Notify`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `event` | `NotifyEvent` | 事件类型 |
| `user_id` | `string` | 发布方有效身份（即 `<effective_user_id>`） |
| `card_id` | `string` | 相关卡片 ID；设备级事件可为空 |
| `card` | `CardInfo` | 相关卡片详情；设备级事件可为空 |
| `reason` | `string` | 人类可读原因，便于日志与排障 |

### 4.8 通知事件 `NotifyEvent`

| 值 | 名称 | 触发时机（Agent 行为） |
| --- | --- | --- |
| `0` | `NOTIFY_EVENT_UNSPECIFIED` | 未使用 |
| `1` | `DEVICE_ONLINE` | MQTT `ConnAck` 成功后首次上线；`reason` 如 `mqtt connected` |
| `2` | `DEVICE_OFFLINE` | 守护进程收到取消信号准备退出；`reason` 如 `daemon stopping` |
| `3` | `CARD_CONNECTED` | 监控发现新卡；或重连后**回放当前卡片快照**（`reason` 为 `card snapshot`） |
| `4` | `CARD_DISCONNECTED` | 监控发现卡片拔出 |

重连语义：每次 MQTT 重新连上并标记 online 后，除 `DEVICE_ONLINE` 外，会把当前会话里已有的卡片再以 `CARD_CONNECTED` 发一遍，避免断线期间的插拔事件丢失。

## 5. 方法调用约定

### 5.1 通用流程

```text
调用方                              Broker                         Agent
  |                                   |                              |
  |-- MethodRequest (method topic) -->|                              |
  |                                   |-- MethodRequest ----------->|
  |                                   |                              | 执行 Operation
  |                                   |<-- MethodResponse -----------|
  |<-- MethodResponse (同 topic) -----|                              |
```

1. 调用方生成唯一 `request_id`，编码 `MethodRequest`，发布到目标设备的 method 主题
2. Agent 解码、执行、编码 `MethodResponse`（带回同一 `request_id`），发布到同一主题
3. 调用方按 `request_id` 匹配；可同时挂起多个未完成请求

### 5.2 `LIST_CARDS`

- 不依赖 `card_id` / `apdu`
- 返回当前 `CardSessionManager` 中的卡片，按 `card_id` 排序后的 `CardSummary` 列表

### 5.3 `GET_CARD`

- 必须提供有效 `card_id`
- 命中则返回完整 `CardInfo`；否则 `success = false`

### 5.4 `EXECUTE_APDU`

- 必须提供 `card_id` 与 `apdu`
- 卡片须已在会话中，否则 `card not found`
- **全局串行**：Agent 内用一把 `ApduExecutor` 互斥锁，保证同一时刻只有一条 APDU 在飞，避免读卡器/卡片并发冲突
- 卡片 I/O 在 blocking 线程池执行，不阻塞 MQTT 事件循环

## 6. 卡片 ID

启用 `pcsc` 特性时，`card_id` 由读卡器名与 ATR 稳定派生：

```text
card_id = hex( SHA-256( reader_name || 0x00 || atr )[0..12] )
```

即 24 个十六进制字符。同一读卡器上 ATR 不变则 `card_id` 稳定；换卡或 ATR 变化会得到新 ID。

未启用 PC/SC 时，默认后端报告无卡，`EXECUTE_APDU` 返回后端未启用错误。

## 7. Agent 侧生命周期（协议视角）

```text
启动 → 加载配置 / 校验凭据
     → 计算 effective_user_id 与 client_id
     → TLS 连接 Broker
     → 订阅 method 主题
     → ConnAck 后：Notify(DEVICE_ONLINE) + 回放 CARD_CONNECTED 快照
     → 循环：
           · 处理 method 请求并回复
           · 卡片监控事件 → Notify(CARD_CONNECTED / CARD_DISCONNECTED)
     → 退出：Notify(DEVICE_OFFLINE)（若当时仍 online）
```

卡片监控按配置的 `monitor_interval_ms`（下限 100ms）轮询后端；队列容量由 `request_queue_capacity` 控制。

## 8. 配置与协议的关系

`QiCardMeshAgent` 配置文件（默认可执行文件旁 `config.yaml`）中与协议相关的字段：

| 字段 | 协议含义 |
| --- | --- |
| `mqtt.url` | 文档/展示用；运行时强制为 `mqtts://mqtt.cyqi.top:8883` |
| `mqtt.username` / `mqtt.password` | Broker 认证；不可为空 |
| `user_id` | 有效身份前缀 |
| `monitor_interval_ms` | 插拔检测周期（实现参数） |
| `request_queue_capacity` | MQTT/事件队列容量（实现参数） |

## 9. 调用方集成要点

1. **编解码**：使用同一份 `qicardmesh.proto` 生成客户端绑定；payload 为 protobuf 字节，不是 JSON
2. **主题**：用目标设备的 `<effective_user_id>` 拼 method / notify 主题
3. **关联**：每个请求自带唯一 `request_id`；在 method 主题上过滤自己的响应
4. **在线感知**：订阅 notify，处理 `DEVICE_ONLINE` / `DEVICE_OFFLINE` 与卡片插拔；上线后的 `CARD_CONNECTED` 快照可当作当前卡列表
5. **APDU**：按 ISO 7816 构造命令字节；解析响应时使用 `data` + `sw1`/`sw2`
6. **并发**：method 主题上允许多请求在途，但 Agent 端 APDU 会串行执行，调用方应接受排队延迟
7. **安全**：凭据仅用于 MQTT 登录；主题按身份隔离，不在主题中携带密码

## 附录：`qicardmesh.proto` 全文结构一览

```protobuf
syntax = "proto3";
package qicardmesh;

message MethodRequest  { request_id, operation, card_id, apdu }
enum Operation         { LIST_CARDS, GET_CARD, EXECUTE_APDU }
message MethodResponse { request_id, success, error, oneof { card_list, card, apdu } }
message CardList       { repeated CardSummary cards }
message CardSummary    { card_id, reader_name, protocol, card_name }
message CardInfo       { card_id, reader_name, atr, protocol, card_name, metadata }
message ApduResponse   { data, sw1, sw2 }
message Notify         { event, user_id, card_id, card, reason }
enum NotifyEvent       { DEVICE_ONLINE, DEVICE_OFFLINE, CARD_CONNECTED, CARD_DISCONNECTED }
```

完整字段编号与注释见 [`protobuf/qicardmesh.proto`](../protobuf/qicardmesh.proto)。
